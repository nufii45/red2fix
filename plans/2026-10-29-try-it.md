## One-screen design

bryl-minimal, the same as the dashboard: white and ink with a gray ramp, Geist for body text, Geist Mono for
uppercase micro-labels, Geist Pixel for the wordmark, page titles and big numbers. Hairline rules, 16 px
cards with soft shadows, and one halftone patch behind the home hero only. **The one exception, from the
brief:** red and green appear only on the verdict and on the red/green evidence lines. Everything else is
monochrome, including emoji, which are greyscaled as in the dashboard. Light and dark follow the system.
Desktop gets a 14rem left sidebar at ≥1024 px. Phone gets a sticky top bar with the menu. The content column is
42rem, or 56rem on `/results`.

Every call has its own empty, loading and error states. Loading is a skeleton on the hairline grid, not a spinner.

- Input: inline errors such as "That isn't a GitHub repo or pull request URL" and "No open pull requests
  in owner/name". A repo that isn't allowlisted gets "Try it only runs on the demo repo for now. Use it on
  your own repo →" (links to `/install`).
- Limits: "Today's 25 free reviews are used up. They reset at 00:00 UTC." and "You've started 3 reviews
  this hour. Try again in N minutes." One waiting at a time: "A review is already waiting. Try again in a
  minute, or watch it: /r/…".
- Run view: run not visible yet (up to 60 s after dispatch) → "Waiting for GitHub to start the run".
  Unknown id after that → "No review with this id". Run cancelled or failed with no artifact → the error
  verdict and a link to the workflow run. Network error while polling → keep the last state, show
  "reconnecting", back off.
- Recent: none yet → "No reviews yet today. Try an example above."

Copy on the home page, plainly: "Reviews run the pull request's code on a GitHub-hosted runner."

## Architecture (as given; details I'm adding)

### Workflow `.github/workflows/try-it.yml` (this repo)

- `on: workflow_dispatch` with inputs `pr_url` and `request_id`. `run-name: try-it ${{ inputs.request_id }}`.
  `concurrency: {group: try-it, cancel-in-progress: false}`. `permissions: {contents: read, actions: read}`.
  `timeout-minutes: 20`.
- **The step names are the contract with the step bar.** Don't rename them without updating `web/lib/steps.ts`:
  1. `Check out the reviewer`: this repo at `github.sha`, `persist-credentials: false`.
  2. `Fetch the PR`: new `scripts/tryit_fetch.py` (stdlib, reuses `gh_spec.spec_for` and `linked_issue`).
     It calls the GitHub API with `github.token`: the PR, its diff, and the linked issue. It writes `pr.patch`,
     `spec.md` and `out/meta.json` (`request_id, pr_url, repo, number, title, base_sha, head_sha, spec_source`).
     It refuses private repos.
  3. `Check out the repo at base`: `actions/checkout` with `repository` and `ref: base_sha`, `persist-credentials: false`.
  4. `actions/setup-python` 3.11.
  5. `Install the repo`: `timeout-minutes: 10`, `continue-on-error: true`. It runs `pip install -e .` if
     `pyproject.toml` or `setup.py` exists, and `pip install -r` for each `requirements*.txt`, plus the
     reviewer's pins from examples/github/red2fix.yml (`openai==3.35.1 pytest==9.1.1 langsmith==0.14.14`).
     No secrets on this step.
  6. `Review` (only if install succeeded): `python -m agent.review --repo ../target …` from **this** repo,
     with `--head-sha`, `--spec-source` and `--number`. Env: `NEBIUS_API_KEY: secrets.NEBIUS_API_KEY_TRYIT`,
     `TAVILY_API_KEY: secrets.TAVILY_API_KEY`, `LANGSMITH_API_KEY: secrets.LANGSMITH_API_KEY`, and
     `LANGSMITH_TRACE_URL_BASE: vars.LANGSMITH_TRACE_URL_BASE`, the same lines as the gate workflow.
     `web_search` comes from the target's base `.red2fix.toml`. No GitHub token.
  7. `Couldn't install`: runs if install failed. A tiny script writes `review.json` with verdict `error`,
     reason "couldn't install the repo", and `review.md`.
  8. `Upload the evidence`: `if: always()`, artifact `try-it-<request_id>`, out/ plus meta.json,
     `retention-days: 30`.
- Per-review budget stays $1, from the policy default and `config.MAX_USD`.

### Vercel API routes (`web/app/api/…`, Node runtime, server-only token)

- `lib/github.ts`: one fetch wrapper with `GITHUB_DISPATCH_TOKEN`. The token is fine-grained, limited to
  nufii45/red2fix with actions read/write and contents read. Public repos are read with the same token.
- `POST /api/review {url}`
  1. Parse: `github.com/o/r` or `github.com/o/r/pull/n`, with trailing paths and `.git` tolerated. Anything else → 400.
  2. Allowlist: `TRYIT_REPOS` (comma-separated, default `nufii45/red2fix-minikit`), case-insensitive.
     Not listed → 403 with `{reason: "not_allowlisted"}`.
  3. A repo URL → `{prs: [...]}` for the picker, with no dispatch. A PR URL → check that it exists (open or closed).
  4. Limits, from one call listing today's try-it runs (`created>=today UTC`):
     daily count ≥ `TRYIT_DAILY_CAP` (25) → 429. **Any run already `queued`/`pending`/`waiting` → 409.**
     GitHub concurrency keeps one running and one pending run, and a third would *cancel* the pending one.
     So "one at a time" means at most one running plus one waiting. Per IP: see below.
  5. `request_id` = 6 hex chars of `HMAC(TRYIT_SALT, ip)` followed by 8 random base32 chars. Dispatch, then return `{id}`.
- **Per-IP limit without storage (user's choice).** Runs list doesn't expose dispatch inputs, so the IP
  tag rides in the request_id, and so in the run-name. The route counts today's runs whose run-name
  starts with `try-it <tag>` and were created in the last hour. More than 3 → 429. The tag is a salted
  hash; it doesn't reveal the IP. The IP comes from `x-forwarded-for` (set by Vercel).
- `GET /api/review/[id]`: validate the id format. Find the run by `display_title == "try-it <id>"` in the
  recent workflow runs, then remember id → run_id in the response so later polls skip the search. Return
  `{status, position, elapsed, steps:[{name,status,conclusion,started_at}], run_url}`. Position = count of
  queued try-it runs created earlier, plus one if something is running. When the run has completed:
  download the artifact zip server-side (unzipped with `fflate`, new dependency), then return
  `review.json`, `review.md`, `meta.json`, `repro_test.py`, ledger totals by model
  (`{nano|ultra|super: {calls, in_tokens, out_tokens, usd}}`, model IDs mapped as in `config.MODELS`),
  `web_searches` and `trace_url` (null if absent), and phase timings from `events.jsonl`.
  Finished results never change, so they get `Cache-Control: s-maxage=31536000, immutable`. Running results get
  `s-maxage=3`, so many viewers share one GitHub call.
- `GET /api/repo-prs?repo=o/r`: allowlisted repos only; open PRs (number, title, author, updated).
- `GET /api/limits`: `{used, cap, remaining}`, `s-maxage=15`.
- `GET /api/recent`: the last 10 completed try-it runs, each with meta.json and review.json read from its
  artifact (cached forever per run id), `s-maxage=30`.

### Step bar mapping (`web/lib/steps.ts`, pure, unit-tested)

| Bar | Driven by |
|---|---|
| Queued | run status `queued`/`pending`/`waiting` |
| Setting up | the steps Check out the reviewer, Fetch the PR, Check out the repo at base, setup-python, Install the repo |
| Writing test, Red on base, Green on PR, Review | while the `Review` step is in progress, **estimated from elapsed time** using the demo runs' measured phase medians (triage+localize+reproduce ≈ 60%, verify ≈ 15%, head check ≈ 5%, review ≈ 20% of ~35 s). The bar never goes past "Review" before the step ends |
| Verdict | the run completed |

The job API only reports workflow steps, and the agent runs as one step. That's why the middle steps
are estimated. They carry a small "estimated" label while live. Once the run has finished, the bar uses the
real phase times from `events.jsonl`.
